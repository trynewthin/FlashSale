# 测试、验证与排障

## 1. 验证层次

### 基础验证

- `go run ./ops/cmd env smoke`

用于检查关键依赖与基础链路是否可达。

### 代码验证

- Go 服务使用 `go test`
- 前端使用 Bun 的测试与构建命令

### 运行验证

- 关注 Compose 服务健康状态
- 检查网关与 `ops-control` 的 `/healthz`
- 必要时核对前端构建产物是否同步到嵌入目录

## 2. 排障顺序

1. 先看基础设施是否健康：MySQL、Redis、Kafka、etcd。
2. 再看迁移是否成功。
3. 再看 RPC 与网关是否进入健康状态。
4. 最后判断前端、媒体链路或运维面板是否存在单点问题。

## 3. 常见问题类型

### 端口冲突

- 典型表现：Compose 启动失败、容器停留在 `Created`、依赖容器无法绑定宿主机端口。
- 处理方式：检查本机已有监听，修改 `configs/deploy.env`，尤其注意 etcd 端口不要落在系统保留区间。

### 依赖未满足

- 典型表现：业务容器本身没有问题，但因为 MySQL、Redis 或 etcd 未就绪而无法启动。
- 处理方式：先修复依赖，再重启业务容器。

### 前端产物不同步

- 典型表现：页面仍显示旧版本、嵌入资源引用错误。
- 处理方式：按串行顺序执行构建、同步嵌入资源和服务重启。

### 媒体链路异常

- 典型表现：上传成功但外部无法访问，或 CDN 正常但管理端写入失败。
- 处理方式：分别检查 `media-store` 鉴权、共享目录和 `cdn` 只读访问链路。

## 4. 测试与排障原则

- 先确认“仓库事实”，再写结论，不沿用过期文档。
- 先定位层级，再深入具体服务，避免一开始就把问题归咎于前端或业务代码。
- 文档只记录当前稳定可复用的排障路径，不保留历史会话噪音。
